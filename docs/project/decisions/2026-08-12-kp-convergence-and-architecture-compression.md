# 2026-08-12: Enter Convergence And Architecture Compression

Date: 2026-08-12
Status: accepted

## Decision

Pause further domain and layout expansion long enough to tighten KP's active
surface. The new active workstream is convergence and architecture
compression: compact project memory, canonicalize language, prune rejected
product representations, make capability dependencies explicit, retire
compatibility beside real caller migrations, improve governed LLM generation,
and then pressure the program-animation seam with TypeScript followed by
Python.

The first learner-facing product remains a goal, but its blocker is described
as **product convergence**, not “solve layout universally.” KP must eventually
select one release-worthy default projection for Public Web v0. Alternate
stacked, split, deck, static, and embed projections remain valid consumers of
the same Article and vignette source and may remain internal experiments.

## Reason

KP's semantic, runtime, publication, authoring, and renderer foundations are
substantial. The repo nevertheless feels sprawling because historical layout
experiments, compatibility paths, broad namespaces, and chronological project
memory obscure the canonical path. Adding more domains before reducing that
surface would increase retrieval cost, regression risk, and model confusion.

The next product proof also needs evidence across unlike content. A symbolic
animation, graph explanation, and code transformation provide a better basis
for choosing a default projection than continued tuning of economics alone.

## Consequences

- `threads/architecture-convergence.md` becomes the active thread.
- The roadmap becomes an operational map rather than a chronological ledger.
- Existing decisions and reviews remain immutable provenance but are not
  startup instructions unless the roadmap or active thread links them.
- Scheme factorial, the algebra pacing contract, and layout experiments remain
  preserved and paused rather than rejected.
- Pruning begins with production reachability and reversible layout removal,
  not a broad source rewrite.
- Compatibility is retired only with caller migration and closure evidence.
- The TypeScript refactor is the next new domain pressure after the compression
  baseline; Python is its second caller.
- SvelteKit, Public Web, and layout selection remain later product gates.

## Alternatives Considered

- Continue adding domain examples immediately. Rejected for now because it
  would expand the surface before proving lower marginal cost.
- Select a universal layout immediately. Rejected because layout should be
  judged against several real content shapes and remain a projection.
- Rewrite the repository into packages first. Rejected because public-entry
  and dependency enforcement can establish the boundary with much less churn.
- Build Public Web before pruning. Rejected because it would force product code
  to absorb known historical representations and compatibility debt.

## Follow-ups

1. Audit production reachability for layout variants, CSS, routes, and tests.
2. Propose the first exact reversible pruning wave.
3. Replace module-registration side effects with explicit capability inputs.
4. Migrate compatibility in caller-backed waves.
5. Build the TypeScript and Python refactor proofs without new runtime owners.
6. Select a public v0 projection and small curated release proof.
