# Authoritative product roadmap projection

Date: 2026-07-23
Status: accepted

## Decision

KP will use the single active approved Theseus plan revision as the structured
authority for product-roadmap items, topic, order, horizon, architecture
benefit, ordering rationale, canonical exemplar, and plan status. Theseus run
contracts and actions remain the sole authority for execution and verification.
The animation catalog, promotion evidence, and development-review history
retain their existing independent authorities.

The Semantic Animation Workbench will project and join those facts without
storing another roadmap or execution state. The structured roadmap will retain
completed capability landmarks and the accepted future arithmetic,
pre-calculus, geometry, data, and cross-domain lanes even when those lanes are
not authorized for implementation.

## Reason

The existing Workbench proves canonical animation identity and independent
lifecycle facets, but its seed bindings are manual and its roadmap coverage is
limited to the immediate execution cohort. Accepted arithmetic, logarithm,
trigonometry, geometry, probability, data, and cross-domain work currently
remains durable narrative evidence rather than one sortable operational
projection.

A single authority per fact prevents the Workbench, project dashboard,
Markdown reviews, and run contracts from becoming competing status stores.

## Consequences

- The generic Theseus plan-phase contract gains reusable roadmap metadata and
  run slices gain an explicit plan-phase foreign key.
- Existing plan-revision and run-contract data remains backward compatible.
- KP activates a successor plan revision containing completed landmarks and
  the full accepted future coverage ledger.
- The Workbench table is read-only and derives every row from the active plan.
- Future or platform rows remain text-only unless a real canonical animation
  relationship exists.
- Arithmetic and later curriculum rows become visible but are not thereby
  approved for implementation.

## Alternatives considered

### Parse the existing Markdown coverage review

Rejected because Markdown structure is not a stable operational contract and
would make presentation prose an implicit database.

### Add a KP-only roadmap sidecar

Rejected because it would compete with Theseus for plan priority and require
new drift reconciliation.

### Store roadmap rows in the Workbench

Rejected because the Workbench is a derived control surface, not a write
authority.
