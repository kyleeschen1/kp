# Twelve-loop horizon: a usable mathematical explanation studio

Date: 2026-11-27
Status: proposed planning horizon, not an approved execution contract.

## Goal and evidence

An author can create a supported mathematical object, discover its available
representations and operations, build a compact linked explanation, revise it
through conversation, and reuse it in a reference page with precise return links.
A new supported example should require source and editorial work, not changes
to a renderer or host application. Failures outside supported families remain
explicit repair gaps.

The accepted quadratic, matrix notebook, column explanation and reference shelf
provide bounded exemplars. Three independently buildable interaction, mathematics
and player lanes provide development boundaries. They do not yet establish a
general authoring SDK, cross-family shelf, integrated LLM revision or broad
mathematical support. This proposal connects those foundations to author work.

This is a planning sequence of outcome-sized loops, not twelve equal-duration
tasks or a promise to finish every row in one execution session. Near-term scope
is firmer; later rows should be revised using actual reuse cost. Each selected
loop needs its finite execution scope and existing visual gates. The proposed
column-geometry successor remains the immediate next action; no priority changes
or implementation are authorized by recording this horizon.

## Proposed sequence

| Loop | Author-visible outcome | Bounded proof and finish |
|---|---|---|
| 1. Link matrix algebra and geometry | Watch matrix columns become weighted vectors and their sum alongside the equation. | Use the existing selected matrix source and one playhead; seek/reverse/reload agree. First host and review are specified in the existing geometry proposal. |
| 2. Discover what an object can do | Select a matrix/vector or quadratic and find applicable operations, views and supported explanations through the existing row picker. | Both families use domain-owned applicability; rows distinguish available, needs input and unsupported. Metadata search does not eagerly load solvers or graphics. |
| 3. Complete one contextual LLM revision | Ask the existing chat to improve the explanation at a selected moment; inspect a proposal, preview, accept or reject it, and continue the conversation. | Start with supported annotation wording and valid targets. Check source and draft revisions; preserve undo and reject stale proposals. A real response trial is needed; mocks alone cannot establish usefulness. No paid model calls are authorized by this plan. |
| 4. Reuse an explanation deliberately | Use one source in a notebook and an independent reference, with explicit independent copy, linked derivation and shared occurrence semantics. | Pressure two consumers, one changed source, reload and local view settings. Reuse existing identity/dependency owners; do not build a universal content database. Live versus pinned behavior must be explicit. |
| 5. Connect algebraic forms to graphs | For supported quadratics, inspect expanded, factored and vertex forms while seeing the same curve. | Domain-checked rewrites and correspondence; repeated roots, degree reduction and unavailable real factorization remain honest. Reuse existing quadratic support. |
| 6. Explain inner product and projection | Create a vector-pair explanation connecting components, projection and dot product. | Euclidean R2 first, with negative, orthogonal and zero-vector cases. Adopt existing semantic and visual owners; one accepted exemplar before promotion. |
| 7. Explain composition and area change | Compare two ordered 2D linear transformations and see how signed area changes. | Finite 2×2 examples with a noncommuting pair and singular collapse; reuse domain product/determinant authority. This does not include eigenvalue algorithms or all linear algebra. |
| 8. Connect circle, coordinates and trig | Create a compact sine/cosine reference with a linked circle point and function view. | Real angles, quadrant signs and wrapping. An angle-addition derivation is a possible successor, not a mandatory hidden extension. |
| 9. Explain accumulation | Show signed area accumulating beneath a supported polynomial and connect it to its antiderivative. | Distinguish signed from geometric area, handle reversed bounds and sign changes. Use exact supported integration; general quadrature and intersection solvers remain separate. |
| 10. Author one reusable 3D explanation | Bind a supported surface and slice to source parameters, then reuse the result outside its experiment. | Begin with the existing saddle/section player; resolve outstanding clipping judgment before promotion. Pressure a different supported surface only after the first review. No renderer replacement or arbitrary meshing. |
| 11. Leave and return without losing context | Open a deeper explanation from an exact object/step and return to the same place; add one authored prediction/reveal using that relationship. | Preserve entry/return context across reload; reuse existing scripted-return evidence where applicable. This proves navigation and a practice affordance, not retention or a learner model. |
| 12. Prove the studio with a reference collection | Assemble a small organized page of accepted examples; create a fresh supported example and make a substantive revision through the product. | No new renderer/host code for the fresh example. Record author effort, engineering intervention, revision latency, complete reader payload and resource lifetime; verify export/reopen and narrow-screen behavior. Publication is separate. |

## Why this order

The linked matrix is the nearest concrete mathematical gain. Discovery makes
existing capabilities usable; contextual revision tests the product thesis early.
Reuse then gives subsequent families somewhere durable to live. Quadratic,
vector, transform, trig, accumulation and surface callers pressure different
mathematical and rendering requirements without pretending they share one AST.
The final two outcomes test the organized reference and exact-return experience
the user actually wants.

| Alternative | Benefit | Cost or risk | Recommendation |
|---|---|---|---|
| More shelf/editor polish first | Convenience | Delays mathematical authoring and real revision evidence | Only fix observed blockers |
| Broad mathematics before product revision | More demonstrations | May multiply bespoke hosts and manual engineering | Interleave product proof early |
| Universal schema/plugin framework first | Potential extension consistency | Speculative boundaries before distinct callers | Extract only demonstrated shared owners |
| This bounded studio horizon | Authoring, reuse and mathematical breadth together | Later domain rows may need subdivision | Recommended, reassess after loops 3 and 6 |

## Parallel development and preservation

After discovery and revision/reuse interfaces are agreed, independent bounded
work can use the existing lanes: interaction owns picker/commands and review UI;
mathematics owns admissible objects, operations and derivations; player owns
projection and lifecycle. Each worker needs a separate worktree and explicit
ownership; one integrator owns shared contracts and the combined exemplar.
This document neither starts agents nor grants a parallel implementation run.

Preserve accepted fraction scrolling, plain reference playback, persisted source
identities, editor history, current chat sessions and domain validation. Keep
KaTeX, Graph2D and WebGL responsibilities explicit. Native static truth, lazy
loading and bounded mounted players remain requirements, not a forced iframe or
single-context architecture. Each loop has a reversible feature/adaptor boundary;
visual rollback must not discard semantic models or saved data.

Keep broad Vim parity, generalized MCP hosting, arbitrary CAS/intersections,
complex arithmetic, eigen/diagonalization, general multivariable calculus,
whole-book infrastructure and public deployment outside this twelve-loop finish.
They remain legitimate later horizons. Some may displace a proposed later row
if the user's priorities change; do not silently add them to the finish line.

## Review and success criteria

Review at three useful scales: one representative whenever a new visual treatment
needs judgment; after loop 3, whether conversation materially improves authoring;
after loop 6, whether a distinct family is becoming cheaper to integrate. If not,
repair the demonstrated boundary before widening the catalogue. Review gates are
not routine permission requests for each internal implementation step.

The final proof is an author opening a reference, selecting a supported object,
discovering a useful operation, producing a checked linked explanation, revising
it in chat, saving/reusing it, and returning to its exact context. Passing tests
cannot establish editorial quality or learning transfer; those require separate
human evidence. No calendar completion estimate is asserted from loop count.
