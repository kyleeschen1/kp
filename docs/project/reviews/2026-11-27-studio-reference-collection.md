## Finite outcome

Give readers one organized starting page for accepted mathematical explanations,
then demonstrate a fresh example and a substantive mathematical revision through
existing product controls. Prefer a lightweight index of canonical hosts over
mounting every renderer on one page: readers can find a question without paying
for animations they have not opened. This delivers organization now; a shared
cross-family persistence or embedding framework would be speculative scope.

Canonical collection: `/experiments/math-reference/`, ordinary semantic HTML
with inherited document tokens. It links matrix columns, R2 projection,
composition, quadratic forms, circle/trig, accumulation and saddle sections to
their accepted hosts. Those hosts retain their semantic objects, renderers and
clocks; the index does no mathematics and owns no player. Preserve their source
identities, saved state, choreography, typography and existing return behavior.
The smallest rollback unit is the additive index and its evidence/tooling.

The fresh example uses the existing matrix notebook and independent reference:
make an independent copy through the editor clipboard, choose columns (2,1)
and (−1,2), and input (1,2). Its contributions cancel horizontally, giving (0,5).
Revise the second weight to −2: the horizontal contributions reinforce and the
result becomes (4,−3). This is a conceptual contrast about signed contributions,
not just a color or label change. Export each revision through the existing
command, reopen it in the reference, retain the first as a separate named card,
and verify identity, source, local playback and reload. No renderer or product
host change is allowed to make this new example work; record an explicit gap if
the workflow fails. Browser automation may operate real controls and the existing
clipboard event boundary, but cannot inject the mathematical document directly.

## Executed proof and limits

`npm run visual:math-reference` passes all eight final Chromium/Firefox cases.
The fresh source was created through the notebook's clipboard handlers and six
numeric fields, followed by Explain, two resource exports, two reference imports,
card naming, seeking, switching and reload. The test does not inject a source
document or arithmetic result. The two actual Chromium exports are preserved as
[cancellation](../../../content/math-resources/reference-collection-cancellation.json)
and [reinforcement](../../../content/math-resources/reference-collection-reinforcement.json).
They share the copied source and result identities, retain the same matrix, and
differ in the second vector coordinate and its revision. The original source
stays unchanged. Each saved card retains its own playhead after reload.

The final automated run measured creation through first export at 7.69 s in
Chromium and 10.27 s in Firefox; the changed weight reached the linked result in
0.65 s / 0.41 s; the complete workflow took 21.32 s / 24.04 s. These are local
automated interactions including locator waits, concurrent verification load and
browser startup effects, not human/model latency or a performance guarantee.
An earlier less-contended run measured about 0.32 s for the same revision.
Author effort remains selecting the contrast, copying, entering values, exporting,
importing and naming; we have not made that a single seamless authoring action.

No new mathematical evaluator, animation, renderer or example-specific host
adapter was needed. One shared preview-bootstrap defect did require engineering.
New regression checks delay all three supported reader imports and exercise live
failure, rejection after cancellation and successful resolution after cancellation:
live errors are visible; retired work cannot publish readiness or mount. Existing
projection and composition narrow-reader, reduced-motion and visibility checks
also pass in Chromium and Firefox (two checks per family). Matrix import/reload
retains one visible equation player and one linked graph; the index has none.
No memory-profiler measurement or universal resource certification is claimed.

Initial verification failures were a test locator tied to document order instead
of source identity, the real Firefox import rejection above, a redundant union
branch in the measurement script, and a startup thread three words over budget.
Each was corrected; no test or budget was weakened. The final 75 project-vision
checks, full type check, focused test types, architecture and tooling checks pass.
The configuration inventory adds only the new scoped browser configuration;
all pre-existing policy hashes are unchanged. Impact selection used its generic
full-repository fallback; this bounded additive candidate uses the affected
checks described here, not the unrelated full unit or publication suites.
