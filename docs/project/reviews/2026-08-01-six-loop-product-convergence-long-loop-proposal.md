# Six-Loop Product Convergence Long-Loop Proposal

Date: 2026-08-01
Status: approved in conversation; executable state lives in Theseus

## Outcome

This long loop turns the current catalogue and architecture inventory into one
coherent product tranche. If no technical stop condition fires, it leaves KP
with:

- an honest, searchable catalogue whose 3D rows have a meaningful native-host
  result and whose ambiguous rows have a compact evidence package rather than
  inferred dispositions;
- one verified generated solve-x session compiled to the canonical animation
  asset and a deterministic, reviewable explanation spine;
- a narrower caller-proven authoring facade with adjacent obsolete paths
  removed only when their last callers migrate;
- a review-ready vector dot-projection exemplar at the stable rank-5 frontier;
- an attributed and repaired catalogue capability-loading path measured against
  the existing bundle, LCP, CLS, interaction, and frame-health targets; and
- a review-ready native addition execution-trace exemplar that closes the two
  observed programming catalogue host gaps without pretending BFS is promoted.

The terminal state is `HUMAN_CHECKPOINT`, not automatic product promotion. The
checkpoint collects the remaining catalogue dispositions, generated-session
editorial/visual judgment, vector visual approval, and programming visual
approval in one review package.

## Canonical References

- Catalogue interaction: `animation.linear-solve.solve-x` in the approved
  persistent catalogue shell.
- Three-dimensional technical language: the existing semantic `Graph3D`
  saddle-surface and curve fixtures, hosted lazily with the same role palette,
  typography, lifecycle, and WebGL lease policy used by retained 3D evidence.
- Generated algebra: the verified linear-problem trace and the canonical
  solve-x `KpAnimationAsset`/reader behavior.
- Explanation: verified claims plus one hand-authored `ExplanationSpineV1`;
  prose does not own mathematical truth or playback.
- Graph language: `kp.dimensional-continuity-graph-presentation-profile.v1`
  and the approved economics/physics captures.
- Vector exemplar: Project one vector onto another, with exact component,
  magnitude, angle, dot-product, and projection correspondence.
- Programming exemplar: the existing deterministic addition execution trace,
  source ranges, locals/output state, and sampled-frame payload.
- Performance: the direct economics catalogue route and the established
  `perf:animation` measurement matrix.

## Observable Acceptance Criteria

The run is ready for human review only when:

1. every concrete catalogue row reports loadability and meaningful native
   hostability honestly; no iframe or decorative placeholder counts as paint;
2. selecting an unneeded capability does not make graph, KaTeX, code, or WebGL
   runtime bytes part of the initial catalogue route;
3. generated solve-x preserves provider provenance, stable semantic selectors,
   exact direct seek/rewind, native KaTeX settlement, and fail-closed unsupported
   presentations through one canonical asset path;
4. the explanation spine contains only verified claim references, approved
   vocabulary, deterministic learner-state choices, and reviewable ordering;
5. public-facade changes are supported by named callers and every deletion has
   a proven last-caller migration in the same rollback unit;
6. the vector exemplar preserves exact symbolic/spatial identity, accessible
   state, responsive layout, one clock, one paint owner, and the dimensional-
   continuity visual language;
7. the measured catalogue route meets the existing product targets or records
   an exact, attributed residual that cannot be repaired without a separately
   approved scope or fidelity tradeoff;
8. the programming exemplar deterministically synchronizes source, current
   range, locals/output, and control state through play, pause, direct seek,
   rewind, static output, and accessibility; and
9. focused, architecture, production-erasure, build, browser, visual,
   performance, promotion-memory, and Theseus integrity gates provide durable
   evidence at their named boundaries.

## Preservation Boundary

- semantic objects, transformations, exact claims, lineage, and source
  provenance;
- deterministic clocks, runtime sampling, direct seek, rewind, and static
  endpoints;
- native KaTeX ownership of settled mathematical typography;
- one canonical renderer/paint owner per mounted projection;
- the approved persistent catalogue shell, simple default controls, lower-left
  Review capture, compact headings, and inline mathematical typography;
- the stable animation-promotion order and all prior release evidence;
- WebGL lease limits, context-loss fallback, and capability-lazy loading;
- accessibility, reduced motion, export/static truth, and direct artifact URLs;
  and
- unrelated user-owned worktree files.

The smallest rollback unit is one verified slice commit. Visual exemplars are
separate rollback units from the shared contracts they may later justify.

## Verification Cadence

Each slice begins and ends with `npm run --silent loop:status`. Focused tests
run inside discovery slices. Typecheck, architecture, build, and browser checks
run when a shared integration boundary changes. Stable visual commands are
extended as committed, scope-specific entrypoints; disposable captures remain
under `tmp/codex/`. The full release matrix is reserved for `s25` and `s30`
unless an earlier shared change makes it necessary.

Every completed slice is one independently reversible commit. The commit may
contain its implementation, focused tests, and the matching Theseus evidence;
it must not absorb unrelated user-owned files.

## Stop Conditions

Stop the run and report the exact terminal reason when:

- another active contract or plan authority cannot be reconciled;
- a catalogue disposition, aesthetic preference, explanation wording choice,
  or promotion decision is required to continue objective work;
- 3D hosting requires a universal renderer, eager WebGL, or another runtime;
- generated solve-x requires provider control of truth, timing, geometry, or
  prose, or cannot fail closed;
- API pruning would delete a live caller, unique conformance evidence, or an
  unrelated user change;
- vector projection requires a new graph engine or cannot represent exact
  semantic/spatial correspondence;
- performance targets can be reached only by widening targets, dropping
  semantic fidelity, or expanding into an unapproved site-wide rewrite;
- programming hosting requires arbitrary code execution, a live language
  runtime, or promotion of the later BFS curriculum family; or
- required verification is missing, contradictory, or cannot be recorded
  durably.

## Explicit Deferrals

- final catalogue Keep/Retire/Rewrite dispositions and deletion of ambiguous
  semantic fixtures;
- vector promotion, motif generalization, and the matrix second caller until
  the vector visual checkpoint is approved;
- programming comparison/composite generalization and BFS promotion until the
  addition trace is approved;
- untrusted/model-authored editorial text, context-output hardening beyond an
  actual shipping caller, and live LLM services;
- the public KP website, curriculum, learner/teacher systems, course-scale
  authoring, and publication rollout;
- a universal renderer, scene graph, motif registry, parameter schema,
  economics/physics engine, or arbitrary code runner; and
- catalogue-wide restyling beyond rules already promoted through approved
  exemplars.

## End-State Review

At `HUMAN_CHECKPOINT`, expect one short index linking four review groups:

1. catalogue truth and disposition candidates, including wide/narrow/fallback
   3D evidence;
2. generated solve-x plus the deterministic explanation spine;
3. vector projection at the exact moments needed to judge rank-5 promotion;
4. programming addition trace at the exact moments needed to approve its
   native surface.

The same package reports the public API diff, retired last-caller paths,
initial-route capability graph, measured Core Web Vitals, passed checks, and
any exact residual debt. Human approval can then be narrow: approve or revise
each visual group and assign only the catalogue dispositions that are clear.
