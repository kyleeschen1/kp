# Animation Catalogue Simplification Next-Step Review

Date: 2026-07-31
Status: approved — recovery closed, successor ready

## Current State

KP has a strong semantic/runtime foundation and more than thirty catalogue
identities currently labelled playable, but its internal experience is split
across a project dashboard, Editor/API Outline, Semantic Animation Workbench,
reader lessons, cards, review galleries, exports, and diagnostic hosts. The
same animation can appear as several selectable representations, with nested
search, many controls, large headings, cards, and iframe boundaries competing
with the animation itself.

The Theseus recovery contract completed all 20 slices with its full release
matrix green. Its final slice transferred execution authority to this catalogue
direction without beginning catalogue implementation inside the recovery
contract. `run-contract.kp.animation-catalogue-simplification-v1` is ready at
its first catalogue-truth slice.

The solve-x asset is the best visual exemplar because it has the widest known
context sprawl while already carrying mature semantic, timing, renderer,
accessibility, and review evidence. Programming execution trace is not a safe
preselected second caller: its asset and timeline exist, but its external port
declares `placeholderContract: true`, and `src/main.ts` registers equation,
diagram, and graph surface adapters without a programming adapter. Its current
“playable” label is therefore exactly the kind of assertion the inventory must
pressure.

Scores are 1–5; lower slice size and risk are better.

## Recommendation

The approved next loop is catalogue-first and contains one mandatory visual
checkpoint. After recovery closeout, perfect the new shell around
`animation.linear-solve.solve-x`. Do not generalize the shell until the desktop
composition is visually approved.

After approval, project every concrete loadable asset through the same host
contract and classify its actual health. This is intentionally a fast catalogue
port: preserve current animation behavior, expose missing adapters and other
gaps, and avoid repairing every artifact during inventory. Review the resulting
library together and assign dispositions before materializing a canonical port
order.

The user approved this proposal through the preceding grill-me decisions and
the explicit instruction to proceed. The successor control record is now
`run-contract.kp.animation-catalogue-simplification-v1`. Source implementation
is bounded by that contract and the solve-x human checkpoint.

## Canonical Exemplar Contract

**Reference:** `animation.linear-solve.solve-x` in its current canonical player,
including the reader and editor behavior protected by
`src/editor/semantic-animation-preservation-manifest.ts`.

**Observable acceptance criteria:**

- `/` opens the catalogue without an “Animation Studio” masthead;
- the solve-x animation is visible without page scrolling and without an
  iframe, prominent card, shadow, or nested surface chrome;
- the left rail offers flat fuzzy asset search and a compact lower-left review
  capture box;
- the universal toolbar shows only Play/Pause and a scrubber;
- keyboard step/reset, direct seek/rewind, and accessibility remain intact;
- the right side has one open inspector, with linear Details and optional
  Parameters or Tuning rather than tabs or nested cards;
- mathematical text is inline by default and visible headings use `h3` scale
  while retaining semantic heading structure;
- the result row shows only title, small domain label, and derived health;
- `/?artifact=animation.linear-solve.solve-x` restores selection; and
- review capture automatically records the artifact and observed state.

**Preservation boundary:** semantic objects and transformations, selectors and
lineage, choreography and phase timing, deterministic play/seek/rewind,
canonical paint ownership, native settled typography, accessibility, artifact
identity, current review history, and non-catalogue consumer contracts.

**Smallest rollback unit:** the new catalogue shell, its default-route wiring,
its solve-x host binding, and its focused checks. The old editor/workbench route
remains available as a hidden diagnostic comparator through the checkpoint.

**Promotion criteria:** explicit human approval of the desktop exemplar plus
passing semantic/clock/ownership/accessibility preservation checks. Approval
promotes the shell treatment only; it does not promote every asset, tuning
value, adapter, or motif.

## Proposed Implementation Phases

### Phase 0: Close recovery and transfer authority

Finish approved recovery slices 17–19 without broadening them. After proposal
approval, revise slice 20 so it records a resolved release baseline and a
catalogue handoff rather than activating economics. Close the recovery contract
with durable evidence, then create one catalogue run contract sourced from this
proposal.

Verification: `npm run --silent loop:status`, the recovery contract's named
checks, clean typed status/evidence, and a closeout classification.

Stop if the release baseline cannot be resolved honestly or if revising the
handoff would discard required recovery work.

### Phase 1: Establish catalogue truth

Characterize the loadable asset registry, current display catalogue,
preservation manifest, surface-adapter registry, review capture, and default
route. Add focused contract tests for one row per concrete asset ID, exclusion
of planned-only work, related-context grouping, and actual hostability-derived
health. Do not redesign the visual shell yet.

Expected areas: `src/animation/catalog-loader.ts`, catalogue projection code,
surface-adapter registry, focused catalogue tests, and a stable
`npm run visual:animation-catalogue` entrypoint whose disposable output lives
under `tmp/codex/`.

Stop if a single existing registry cannot distinguish asset existence from
hostability without inventing duplicate lifecycle authority; record the seam
and propose the smallest typed split.

### Phase 2: Build the solve-x shell exemplar

Implement the default three-region desktop shell for solve-x only: flat left
search/results, frameless persistent stage, minimal player, one right
inspector, inline math scale, compact lower-left capture, and selected-artifact
URL. Reuse existing runtime, renderer, controls, and review capture paths. Keep
bespoke inputs behind Parameters or Tuning and keep the old route as a hidden
diagnostic comparator.

Verification is deliberately focused during discovery: catalogue identity and
route tests, solve-x semantic/timeline/seek/rewind/ownership/accessibility
checks, one Chromium smoke flow, and `npm run visual:animation-catalogue` at the
desktop review viewport. Do not run or encode the full aesthetic certification
matrix yet.

Rollback unit: one independently reversible shell exemplar change.

### Human checkpoint: select the shell

Stop and present the running desktop solve-x catalogue to the user. Review
tiling, stage prominence, control density, typography, inspector behavior,
search density, and review capture. The only valid outcomes are approval,
bounded revision of the exemplar, or rejection/rollback. No sibling asset is
generalized before approval.

### Phase 3: Promote the approved shell boundary

After approval, make the catalogue the default internal home, retain the old
Editor/API Outline and workbench only as named diagnostic routes, and formalize
only the approved responsive, focus, keyboard, and inspector behavior. Add the
motif-specific UI regressions revealed by review; keep narrow mode to an
accessible overlay rail/inspector rather than a polished phone design.

Verification: focused unit and browser tests, approved desktop checkpoints,
keyboard and focus behavior, one narrow functional smoke, typecheck, and
architecture checks.

### Phase 4: Run the fast catalogue-wide host pass

Project every concrete loadable asset through the standard host contract, one
top-level row per asset ID. Dispatch to existing domain adapters. Do not use
iframes and do not repair missing renderers merely to make the health count
look good. Derive `Ready`, `Review`, or `Broken` from observable host,
diagnostic, and review evidence. Keep detailed maturity and compatibility in
Details.

Verification: registry/index uniqueness, lifecycle honesty, every listed
artifact either paints exactly one primary host or produces an explicit
capability gap, no planned-only rows, no iframe fallback, and the stable
catalogue visual command. Pressure the approved shell with at least one
structurally distinct already-hostable caller, but do not label it the next
canonical port merely because it renders.

Stop if generalization requires a universal renderer, a parallel runtime, or
asset-specific exceptions in the shared host contract.

### Phase 5: Generalize progressive disclosure and capture

Populate the stable linear Details order from existing semantic,
transformation, motif, render-target, capability, verification, review, and
related-context sources. Generalize semantic Parameters and artifact-local
Tuning only where typed inputs already exist. Ensure review capture attaches
artifact ID, playhead, parameters, tuning, viewport, screenshot, and build
identity without a representation picker.

Verification: source-of-truth and empty-section tests, parameter/tuning
separation, state capture/restore evidence, production review-closure check,
keyboard capture, and no duplicated review history.

### Phase 6: Audit together and derive the port queue

Expose the human disposition field under Details and saved queries for health
and disposition. Produce a durable inventory review summarizing asset count,
hostability, capability gaps, related-context sprawl, duplicate/superseded
paths, and likely high-information repairs. Browse the catalogue with the user
and assign initial dispositions. Only then propose a canonical port order using
information gained per effort.

This phase does not implement canonical ports, economics, programming trace,
the public website, or broad cleanup. It ends at a human planning checkpoint
with a reviewed next tranche.

## Verification Cadence

During the solve-x discovery slice, test durable truth and one desktop browser
flow. After visual approval, add the approved shell regressions and one
structurally different caller. Run the full relevant unit suite, typecheck,
architecture checks, production review closure, and broader browser coverage at
the catalogue promotion boundary—not before the aesthetic treatment is
selected.

All browser-driving visual checks must live in a stable repo-owned script or
test exposed as `npm run visual:animation-catalogue`; screenshots and reports
remain disposable under `tmp/codex/` unless later adopted as reviewed goldens.

## Explicit Deferrals

- economics and physics promotion implementation;
- programming execution-trace repair or canonical-port status;
- a three-artifact or other public website launch;
- full curriculum, learner accounts, teacher tooling, and phone polish;
- live LLM editorial generation or a broad explanation-track buildout;
- universal renderer, scene graph, or global control schema;
- full canonical-port ordering before the catalogue audit;
- broad deletion of old routes before their unique evidence is inventoried.

## Stale-Plan Notes

- The previously discussed three-artifact public launch is rejected as an
  active next step. Publication contracts remain useful boundary evidence, but
  any current instruction to implement that launch before the catalogue audit
  is stale.
- Statements that make the project dashboard or Semantic Animation Workbench
  KP's primary internal operating surface are superseded by the asset-first
  catalogue decision.
- Statements that call economics the immediate execution frontier now mean only
  that it remains the first unresolved domain-promotion rank. They do not
  authorize an economics proposal or implementation during this tranche.
- Programming execution trace remains an implemented semantic fixture and an
  inventory probe. Any assertion that it has already been selected as the
  verified second catalogue caller or next canonical port is stale.
