# Compositor Ownership, Balanced Operations, and Log-Base Long-Loop Proposal

Date: 2026-08-18
Status: proposed; explicit approval required before execution
Proposed contract id:
`run-contract.kp.compositor-balanced-log-base-convergence-v1`
Target: `workflow.kp.delivery`

## Objective

Restore the canonical native-KaTeX compositor's sealed ownership gate without
changing accepted motion, then consolidate existing both-sides equation
operations into one governed generation family, and finally pressure the new
boundary with one alternative-base logarithm exemplar.

The end state should make new equation generation cheaper and more reliable:
the compositor consumes renderer-ready scene plans instead of accumulating
operation planning, authors can name a verified both-sides transformation
without choosing historical adapters, and explicit logarithm bases survive
normalization, semantic identity, change-of-base truth, and motion.

## Why This Loop Is Current

The previous generation-foundation contract is resolved. Its new Coverage view
correctly identifies balanced operations as an exemplar family, but a focused
health review found that the canonical-renderer dependency closure now exceeds
its fixed source ceiling by 14,245 bytes. Runtime evidence is green, so the
highest-leverage move is a behavior-preserving ownership correction before
asking the same boundary to absorb another generated family.

Balanced-operation consolidation is next because subtract, multiply, divide,
and apply-log already provide contrasting callers. Alternative-base logarithms
then supply one genuinely new syntax and motion pressure case, rather than
another internal-only abstraction exercise.

## Allowed Work

- source/dependency attribution for the canonical native-KaTeX compositor;
- explicit renderer-session versus ephemeral scene-plan compiler ownership;
- separately enforced source and bundle budgets that cannot hide moved code;
- migration of existing canonical reader, catalogue, log, and equation callers
  through the clarified plan/render boundary without visual change;
- one typed both-sides semantic family with operation-specific law and domain
  evidence, a shared causal recipe, governed authoring, and fixed corpus;
- explicit-base logarithm parsing/normalization and change-of-base semantics;
- one reviewed native-KaTeX change-of-base exemplar;
- focused tests, stable visual entrypoints, project memory, and closeout.

## Disallowed Work

- raising the failed source ceiling merely to make the gate pass;
- relocating code into an unmeasured helper or broad barrel;
- changing approved choreography, timing, geometry, semantic endpoints,
  identity, correspondence, optical profiles, or equation order;
- a second clock, renderer, compositor, scheduler, or durable scene graph;
- a universal CAS-style “apply anything to both sides” operation;
- inferring truth or lineage from LaTeX text or glyph equality;
- arbitrary roots, powers, inequalities, matrices, code, Graph2D, or Graph3D;
- public layout, curriculum, SRS, tutoring, or live-model integration;
- edits to user-owned economics files or unrelated documentation.

## Architecture Contract

The renderer boundary remains:

```text
verified semantic transformation
-> ephemeral presentation/scene-plan compilation
-> renderer-ready measured tracks and ownership
-> one native-KaTeX renderer session
-> exact native endpoint settlement
```

The renderer may measure native paint, sample tracks, own inert transit paint,
and settle endpoints. Operation choreography, collision policy, semantic motion
projection, and successor planning must be compiled before the final paint
session unless measurement makes a small renderer-local decision unavoidable.
Every extracted responsibility remains independently measured.

## Visual Reference And Promotion Gate

All existing callers are preservation references, not redesign targets. Their
accepted contact sheets and deterministic frames must remain unchanged within
existing tolerances.

The only new subjective work is the change-of-base exemplar, proposed as:

```text
log_2(7) -> ln(7) / ln(2)
```

The base `2` must retain semantic identity as it becomes the denominator's
argument; `7` must retain identity as the numerator's argument; the source log
operator must hand off causally to the two target operators without suggesting
that glyph copies establish mathematical truth. Native function-wrap reception
remains the enclosure reference. Slice s28 stops for explicit human review.
Slice s29 is not authorized until that checkpoint is approved.

Promotion requires readable identity continuity, direct seek/rewind, no glyph
collision or endpoint snap, no new compositor primitive, and a structurally
different pressure case reserved for later family promotion.

## Verification Cadence

- Discovery and ownership slices use exact inventories, type laws, and the one
  specialized source gate; they do not run browser matrices.
- Shared planner/renderer migrations run the relevant glyph, presentation, and
  reader suites at each boundary, not after every mechanical move.
- Existing visual behavior is a preservation gate throughout Tranche A and B.
- The new log-base treatment receives only smoke checks until the s28 human
  checkpoint; motif regression and structurally different caller pressure wait
  until approval.
- Release runs impact-selected tests, typecheck, Internal Studio and product
  builds, bundle boundaries, stable visual checks, and Theseus validation.

## Commit Cadence And Rollback

Each slice is one independently reversible commit containing implementation,
focused verification, and completed Theseus evidence. The compositor ownership
map, plan contract, each extracted responsibility, each caller migration, the
balanced family, each operation cohort, log-base semantics, and the exemplar
are separate rollback units. Exact path staging must exclude protected user
files.

## Contract Stop Conditions

- existing semantic or visual behavior changes outside the new exemplar;
- the failed compositor gate is cleared by raising a ceiling or hiding bytes;
- aggregate source or bundle attribution becomes weaker;
- a second renderer, clock, scheduler, lifecycle, or paint vocabulary appears;
- both-sides generalization accepts unverified algebra or erases distinct
  domain assumptions;
- a central closed switch grows where a declaration/registry should extend;
- the log-base work expands into arbitrary logarithm/CAS support;
- user-owned dirty files overlap required edits;
- human visual judgment is required at s28.

## Expected End State

Before the human checkpoint, KP will have a green and honestly measured
compositor ownership boundary, one generated balanced-operation family over
existing approved callers, and one typed change-of-base exemplar ready for
review. It will not have a universal equation solver, arbitrary logarithm
support, or permission to generalize the new visual treatment.
