# KP Bundle And Application Isolation Closeout

Status: complete
Completed: 2026-08-16
Run contract: `run-contract.kp.bundle-application-isolation-v2`

## Outcome

Tranche B is complete. KP now measures selected experiences from Vite's
production manifest, loads heavyweight renderer capabilities behind literal
boundaries, and builds Internal Studio and each current Public Web proof as
independent production graphs. Development review code is mechanically erased
from production, dashboard rendering no longer owns data startup, the algebra
solve closure is split only where measurement proved value, and five narrow
framework-neutral facades have transitive dependency enforcement.

No choreography, semantic identity, public URL, static publication, clock,
seek/rewind behavior, native endpoint, accessibility output, or user-authored
economics source was deliberately changed.

## Ownership Changes

- Typed bundle scenarios describe entry, activation, script, style, asset,
  and dynamic-boundary closure from one production manifest.
- Native KaTeX has one immutable feature-pack contract and literal lazy
  implementation. Reusable adapters remain Node-importable; Internal Studio's
  catalogue route owns the shared KaTeX typography needed before first paint.
- Place-value metadata and semantic startup remain cheap while its native
  renderer loads only after selection.
- Internal Studio owns `studio/index.html` and
  `vite.internal-studio.config.ts`; current public proofs each own a dedicated
  Vite graph instead of entering through the shared development build.
- Production entry inspection rejects development review, toolbar, capture,
  and save implementations from rendered module graphs.
- Algebra's base pack and linear-solve pack retain one shared choreography
  authority without duplicating runtime code.
- `src/public/{semantic,runtime,renderer,authoring,publication}.ts` are explicit
  framework-neutral facades. Their complete transitive closures reject Svelte,
  product hosts, undeclared packages, and deep unsupported public targets.

## Physical Package Readiness

Logical packages are ready for a second-host proof, not yet for physical
`@kp/*` extraction. Semantic and runtime facades have the strongest future
package boundary. Renderer and publication facades deliberately retain web
and KaTeX dependencies. There is still only one first-party repository release
cadence, so physical packages would add versioning, exports, build, and testing
cost without an independent consumer proving that value.

The next extraction gate is a plain-HTML or second independent host consuming
the enforced facades without deep imports. If that succeeds, extract semantic
and runtime ownership first; keep application composition and Svelte in host
packages, and evaluate renderer/publication extraction only from measured
consumer pressure.
