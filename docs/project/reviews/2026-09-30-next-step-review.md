The subsequent matrix animation and API discussion led to the

The source-to-artifact question below remains useful, but distribution/inspector

The user found the first inspector's purpose unclear. This is evidence that the
exemplar did not communicate its purpose to its intended reviewer; it is not

its unaccepted human checkpoint. No factoring or promotion is authorized by
this strategy question.

## Recommendation

Define and demonstrate one complete author task: supply a supported symbolic
step, obtain its existing canonical animation, and recover what the system
actually knows about that step. Prioritize that source-to-artifact workflow
before further inspector polish or another reference page. Initially treat the
user as the author/toolmaker; this is an experiment participant, not a settled
market choice.

The bounded candidate uses the existing distribution owner. Show its current
source beside the resulting animation; then change a supported coefficient or
addend and record all work required to produce the second artifact. Inventory
the accepted authoring path first: do not assume arbitrary input support or
weaken the exact-preview guard. Report source edits, manual semantic bindings,
host integration and engine edits separately. Reuse existing test/harness and
host seams; no editor, SDK, importer or new renderer is implied.

Use one concrete inspection question: “Where did this factor go?” Show the whole
factor and its two descendants as the intended explanatory unit. Any new visual
treatment needs a bounded exemplar review; do not silently replace occurrence
identity with glyph matching. Keep IDs and diagnostic details in an optional
developer disclosure. Explain the mathematical reason separately from the
implemented checks; a declared distributive law is not an executed proof.

First deliverable should be a short source-to-result walkthrough and an honest
authoring-cost comparison, using existing machinery wherever possible. Success
means the user understands what is authored, what is generated, and what can be
trusted, and a supported variation requires bounded, explained effort. This
does not establish comparative novelty, learning gains or a market.

## Alternatives

Scores are local judgments, not measurements; 5 is high, including risk.

| Candidate | Authoring | Reliability/demo value | Reuse information | Speculative risk | Recommendation |
|---|---:|---:|---:|---:|---|
| Complete source-to-artifact walkthrough and supported variation | 5 | 4 | 5 | 2 | Scope next |
| Polish the current occurrence panel | 1 | 2 | 2 | 3 | Defer until the task is clear |
| Continue factoring/generalization automatically | 3 | 3 | 4 | 4 | Preserve conditional queue; do not resume |
| Build a general symbolic workbench or SDK | 4 | 2 | 3 | 5 | Defer |
| Author more similar pages | 2 | 3 | 1 | 3 | Only for a named capability question |

This approach reduces stale parallel planning by amending the existing proposal
if accepted, rather than starting another long loop. It preserves the current
semantic evidence and renderer, keeps the experiment small, and creates a
durable account of author effort. The existing proposal already contains a
later source-variation trial; moving that question earlier requires an explicit
order/scope amendment, not silently skipping the visual gate.
