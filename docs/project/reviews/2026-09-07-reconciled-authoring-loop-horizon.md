### R1 boundary and success

Start with approximately 24 representative deduction chains as a bounded
diagnostic corpus, not a statistical coverage claim or a mandate to implement
every row. Separate notation, semantic operation, assumptions, verification,
motion, generation and publication readiness. Repair the documented coverage
evidence-wiring gap if confirmed against current code; do not change labels
without executable evidence. Measure three author tasks: wording, supported
parameter, and step/detail edits. Record manual glue and specialist intervention.

Reuse the existing file/editor and local preview authority. No editor rewrite,
new browser write endpoint or untrusted source execution. LaTeX is an input
language, not sufficient proof of a transformation. Start real-model smoke
after the bounded entrypoint is coherent; unavailable model access is a named
evidence gap, not permission to call fixtures a live trial.

Success: a bounded author/model packet produces, breaks, repairs and publishes
one coherent revision without handwritten renderer glue or silently stale facts.
Static editions remain reproducible; shared form changes propagate on rebuild,
not by mutating previously distributed immutable files.

### R2 boundary and success

Use one supported distribute-then-evaluate procedure and one bounded parent
claim/reason path. Do not invent a universal knowledge ontology or treat free
prose as machine-proved. Distinguish domain evidence from editorial explanation.
Extraction preserves assumptions, referents, source revision and the return
address. Answer state is not semantic truth. Reuse existing flashcard machinery;
do not add accounts or a scheduler.

After the first visual checkpoint, pressure the necessary shared boundary with
the existing extract-helper code caller, retaining language-specific semantics.
Later matrix multiplication invoking dot products provides a different nested
procedure test; it does not reactivate a tabled visual asset automatically.

Success: a useful reason is backed by explicit structure, not merely a tooltip,
and full, compact and retrieval views stay consistent after source changes.

### R3 boundary and success

Bayes remains the first new flagship; earlier algebra is an integration fixture,
not an inserted competing flagship. Tree reordering preserves joint probabilities;
conditioning changes the reference population; neither reverses causation.
Do not infer independence or fabricate zero-mass conditionals. Use original or
permission-cleared content rather than copying restricted course handouts.

Success: a second problem reuses the domain operations and reviewed mechanisms
mostly through changed source and explanation, not a second animation implementation.

### R4 boundary and success

This consolidates work started in R1–R3; it is not permission to defer all LLM
usability testing until the end. Benchmark actual first output, diagnostics,
repair and held-out variants. Keep code and Graph3D as explicit boundary tests,
not universal equation semantics. Generate repetitive plumbing only where earned.

Promote a demonstrated tier as soon as evidence and approved scope permit;
R4 is not a mandatory barrier delaying useful family work or a broad cleanup
project. Retire obsolete authority beside each migrated caller. Unsupported
tiers remain internal or typed gaps. No automatic catalogue-wide migration.

## Mathematical expansion waves

These are the remaining planned subject horizons, not six whole-course shipping
contracts. Each wave may require several exemplar-sized loops. Reuse existing
capabilities and implement only measured gaps. The default order follows
prerequisites; pull a bounded later caller forward to test a current mechanism
without creating concurrent queues. Probability begins early with R3.

| Wave | Scope | Distinct obligations |
| --- | --- | --- |
| M1 — Algebra/precalculus core | Substitution, collection/factoring, fractions, exponents/logs, relations/inequalities, restrictions/branches, finite binders, multiline chains | Coherent expression identity; assumptions and domain restrictions; broad reuse before cosmetic variants |
| M2 — Trigonometry and calculus AB core | Trig identities, limits, chain/product/quotient derivatives, integration/substitution, accumulation and FTC | Connect symbolic procedures to geometric meaning; keep limit, equality and approximation claims distinct |
| M3 — Calculus BC extensions | Integration by parts/partial fractions, sequences/series, Taylor and error, parametric/polar reasoning, bounded differential equations | Convergence, approximation error, initial/domain conditions; not endpoint matching alone |
| M4 — Linear algebra | Dimensioned products, row operations/systems, basis changes, projections, rank/null spaces and eigen reasoning | Shapes, operand order, algebra/geometry correspondence; nested dot-product procedures; retain existing typed matrix owners |
| M5 — Multivariable calculus | Partials/gradients, Jacobian chain rule, local linearization, multiple integrals/change of variables, vector fields and line/surface reasoning | Coordinate and dimensional meaning; reuse Graph3D without a new universal renderer |
| M6 — Probability/statistics beyond Bayes | Counting, independence, expectation/variance, transformations, sampling distributions and inference | Distinguish data, model, assumptions, conditional statements and inferential conclusions |

For each bounded family run: select an author task, implement missing semantic
or presentation capability, review one representative new motif, pressure a
structurally different caller, then promote only supported cases. Do not claim
coverage from a spelling inventory or a passing parser. The current matrix
promotion-ledger item remains tabled until explicitly reselected.

## Minimal-interruption execution policy

The user's standing request is accepted now and persists across sessions.

- Before a new long run, present one consolidated scope/stop/visual-checkpoint
  proposal for approval, not separate approvals for each phase or technical choice.
  This planning request does not itself approve unseen implementation slices.
- Within approved scope, choose conservative defaults and continue tests,
  diagnostics, repairs, documentation and commits without routine user check-ins.
  Updates are informational, not requests to approve progress. Do not request
  another resume after accepted visual review if approved work remains.
- Aim for one coherent visual review packet per new exemplar/family. Batch
  independent visual questions when safe, but never implement dependent
  generalization while waiting for its prerequisite visual approval.
- Every visual request includes a working browser URL on the shared server,
  the exact artifact/revision, what changed, a short inspection script, the
  decision needed and the recommended default. Do not ask the user to debug
  startup or infer which page they are reviewing. If server availability is
  genuinely blocked, say so rather than presenting an unverified working URL.
- After visual approval, perform technical hardening, the structurally different
  caller and broad release verification autonomously inside the approved scope.
  Unchanged visuals do not receive ceremonial reapproval. A materially new
  interaction/treatment or significant deviation from the approved exemplar
  needs a bounded additional visual review, not assumed approval.
- Still stop for missing execution authority, material scope expansion, unsafe
  actions, new spending/access requirements or a genuine external blocker.
  No budget increases, weakened assertions, automatic merge/deploy, blanket tool
  permissions or unlimited mathematical coverage are implied.

One review per exemplar is a target, not a guarantee: rejected visuals may need
another pass. Prefer early reversible exemplars and cheap preservation checks;
run dense responsive/cross-browser release checks after visual choices settle.
