# Reader activation attribution

Scope: the approved [bounded investigation](../2026-10-21-reader-activation-investigation.md).
Existing canonical tax source, SVG host and three deferred companions are the
complete consumer; no timing or visual treatment is being redesigned.

## Diagnosis

`npm run build:bundle -- --sourcemap` followed by `npm run
audit:architecture-cost -- --browser --tax-only --activation --tax-profile`
separately attributes startup, the first tax transition, and each deferred card.
Profiles are instrumented evidence, not ordinary latency measurements. Generated
helpers without maps retain explicit unmapped labels; inclusive samples overlap.

Three 6x startup profiles attribute 317–322 ms inclusive to swept camera fitting
for the surface-contour companion, before its interactive capability activates.
The fit projects thousands of points and recomputes the unchanged camera basis
for every point. Complete warm Node authority preparations measure medians
42.42 / 47.19 / 15.44 ms for fields (1,2), (.25,4), (4,.25), respectively.
`npm run measure:camera-fit` reports exact fitted-plan digests for preservation.

Startup also forces layout while setting the initial native scroll position.
The first-transition profile includes 198–219 ms inclusive in logarithm native
preparation; that work is not wholly tax-animation work. Later activation windows
can include a previously started companion transition, so their whole-window
CPU must not be attributed solely to the newly activated card. Preserve the
current visibility/interaction policy in this pass.

The audit initially failed before browser execution with `ENOBUFS` because
enumerating all tracked repository paths exceeded the subprocess buffer. It now enumerates
only the four roots already selected by the old filter; an actual Git parity
test guards complete membership. The next attempt encountered `ENOENT` for a
generated helper without a map; explicit unmapped accounting repairs that tool assumption.
Both errors are investigation-tool failures, not reader regressions. Three
profiling/inventory tests and Node typechecking pass.

## Camera-basis repair

The existing graph projection owner now provides a batch call that constructs
one camera basis for that call. Swept fitting uses it for each camera sample.
The single-point API remains compatible and delegates to the same formula.
There is no retained cache, new camera policy or reduced fitting coverage.

Twenty-five focused graph/surface tests pass. Three pre-change fitted-plan
digests remain byte-identical, covering the canonical field and opposite
coefficient extremes. The independent Three.js projection comparison now
checks 26 points at each of five transition positions. A camera-read regression
requires one basis per batch and a fresh basis on the next call. The first test
attempt used an incomplete graph fixture; it was repaired with a real issued
stage graph. The first typecheck found the now-unused single-point import in
the fit module; that import was removed.

Complete Node preparation medians changed from 42.42 → 18.30 ms, 47.19 →
19.63 ms, and 15.44 → 6.59 ms for (1,2), (.25,4), and (4,.25). These are warm
CPU diagnostics with identical outputs, not reader startup promises.

Ordinary production cohorts use `npm run audit:architecture-cost -- --browser
--tax-only --activation --acceptance` without profiling, three fresh contexts
at each CPU rate. At 6x, startup script samples were 903.58/782.75/768.60 ms
before and 688.28/659.76/673.58 ms after; medians improve 13.9%. Readiness
medians are 1,351.90 → 1,278.40 ms (5.4%), with overlapping ranges and no
field-device claim. Initial requested JS is 387,663 → 387,681 gzip bytes
(+18 bytes); loading acceptance passes with no budget change.

First-interaction maximum frame gaps remain noisy: before 282.5/200.2/250 ms,
after 266.8/232.3/316.5 ms. No interaction-smoothness improvement is established.
The repair reduces real startup computation; it does not solve the separate
native preparation/layout stall or justify changing companion activation policy.

The next performance question is the first visible logarithm card's native
preparation: separate source/target measurement and material construction before
choosing a repair. The current evidence does not justify hiding the card,
delaying first input, dropping native endpoints, or changing its visibility
trigger. Forced initial page layout is also visible, but moving the same layout
flush elsewhere would not itself be a performance improvement.

Reproduce the tooling laws with `node --test scripts/architecture-cost-inventory.test.ts
scripts/profile-gradient-cost.test.ts`. The profile command requires a local
sourcemap build; the ordinary timing/acceptance command uses a normal production
build. Never compare instrumented frame gaps with ordinary timing as if they
were the same measurement.
