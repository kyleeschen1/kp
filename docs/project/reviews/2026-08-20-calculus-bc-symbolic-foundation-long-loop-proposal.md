## Why This Loop Is Current

The reconciled generated transformation ledger has 19 equation capabilities: 6
are `Direct`, 4 `Registered`, 2 `Exemplar`, and 7 `Missing`. KaTeX can paint
most prerequisite and Calculus BC notation, and the narrow equation runtime
already supplies identity, deterministic time, direct seek/rewind, canonical
motifs, measured native paint, governed discovery, and typed repair. The main
gap is no longer generic animation machinery. It is explicit semantic coverage
for new syntax and operations.

This contract creates an honest curriculum-scale coverage envelope, then
advances only the first accepted families. It does not claim that one run makes
all Calculus BC transformations visually canonical.

## Contract Boundary

Objective: establish the generated symbolic-mathematics coverage atlas; take
exponential homomorphism and root inversion through independently reviewed
exemplar/pressure gates; and build one reversible equivalence-frame exemplar
over an already verified log transition.

Allowed work:

- equation-domain semantic types, normalizers, operations, recipes, motifs,
  Native KaTeX realization, generated declarations, catalog integration,
  focused tests, exact URL state, visual checkpoints, and project/Theseus
  evidence required by the stored slices;
- one data-derived curriculum coverage projection extending the existing
  Transformation Coverage source;
- existing shared homomorphism, balanced-operation, root, compositor, clock,
  review, and catalogue seams when a slice supplies direct evidence.

Disallowed work:

- code, Graph2D, Graph3D, matrix, large-operator, differentiation, or
  integration implementation in this contract;
- a CAS, theorem prover, universal expression language, new clock, scheduler,
  paint owner, layout system, public lesson, or curriculum UI;
- broad migration of historical equation assets;
- promotion past any human visual checkpoint without explicit approval;
- caller-authored geometry, timing, opacity, DOM, or renderer nodes.

Preservation boundary: all approved log-product, log-quotient, balanced
equation, fraction, evaluation, catalogue, direct-link, accessibility, and
bundle behavior remains unchanged unless the exact slice names it.

Rollback: one focused commit per slice. A visual candidate and its local
registration are one independently reversible unit; promotion is a later,
separate unit.

Estimated envelope: 30 slices across several human-gated sessions, roughly
12–20 hours of implementation and verification if checkpoints are reviewed
promptly. The first mandatory stop is slice 13.

## Verification Cadence

- Focused slices use the exact unit/generation checks named in the table and
  `npm run verify:impact -- --path <changed-path>` to select additions.
- Boundary slices use `npm run verify:equation:boundary`, typecheck,
  architecture checks, and Theseus validation as indicated.
- Promotion and closeout use `npm run verify:equation:promotion` or
  `npm run verify:equation:release`; broad cross-browser work waits until after
  the relevant human visual approval.
- Reuse one committed scoped visual entrypoint and disposable outputs under
  `tmp/codex/`; do not create changing scratch browser scripts.
- Commit every completed slice with its Theseus evidence. Emit
  `npm run --silent loop:status` at slice start, completion, commit boundary,
  and every 30 minutes during a long check.

## Contract Stop Conditions

Stop with the named outcome when:

- slices 13, 18, 25, or 30 require human visual judgment (`HUMAN_CHECKPOINT`);
- source/target mathematics, branch/domain evidence, or canonical ownership is
  ambiguous (`STOP_CONDITION`);
- work requires a new clock, scheduler, paint owner, universal renderer, CAS,
  or another domain (`STOP_CONDITION`);
- an approved existing caller changes perceptibly without being named in the
  slice (`STOP_CONDITION`);
- tests expose unrelated user-owned work that cannot be preserved (`BLOCKED`);
- the 30-slice contract is exhausted (`CONTRACT_EXHAUSTED`).

## Expected Learning

At the first checkpoint, KP should reveal whether the shared homomorphism law
truly supports a power-application realization without copying log behavior.
At root pressure, it should reveal whether semantic branch evidence can govern
motion without becoming choreography. At the final checkpoint, it should show
whether one verified transition can support both replacement and persistent
equivalence without duplicated semantics or paint ownership.
