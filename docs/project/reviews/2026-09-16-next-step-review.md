# KP machinery: reference passages and deliberate transfer

Status: recommendation for discussion, not a new execution contract.
User asks which development work advances reusable KP machinery without turning
the personal classical-mechanics curriculum into a costly publishing programme.
The earlier pruning discussion remains a proposed editorial direction; this
review does not activate that edit or a new implementation loop.

## Recommendation

Use a small set of polished reference passages, then require deliberate transfer
before authoring many lessons. Keep mechanics as a source of authentic learning
friction. A passage earns engineering time when it tests a named reusable
capability or repairs an already-observed shared failure. Stop local polish once
the interaction is clear, reliable enough to test, and no new structural question
is being answered.

The next bounded experiment should transfer the accepted equation-reading
behavior: first unfold an existing checked refinement in the middle of an
argument, retaining downstream context; then demonstrate reuse in the existing
independent scalar caller. Extract only the boundary these callers require.
Measure author changes separately from engine intervention. After that, use the
existing centroid example to test persistent text coordination across code.

## Evidence and limits

- `src/tutorial/mechanics-relations/energy-refinement-unfolding.ts` explicitly
  requires namespace energy and a terminal refinement. It preserves native
  records and prose, but is an exemplar adapter, not a general unfolding API.
- `src/semantic/momentum-energy-derivation-plan.ts` already supplies checked
  norm-scaling child reasoning for a nonterminal energy move. This is a candidate
  pressure source, not a claim that its new inline reader is implemented.
- The scalar reader shares domain-checked binding, compositor and scaffold, but
  its authoring packet admits one bounded cancellation shape. New prose/symbols
  are supported within that shape; arbitrary derivation authoring is not proved.
- `src/tutorial/code-reasoning/centroid-inspection.ts` shares the clock and native
  code renderer but uses its own inspection controls and replaces narration text.
  Accepted motion does not establish persistent code/text coordination.
- Concept dependency reuse is implemented with pinned sources inside mechanics
  publication. The dependency thread explicitly excludes general cross-document
  concept-library claims.
- Viewport and disclosure helpers now occupy reader runtime boundaries, while
  much interaction orchestration remains in the mechanics reader. Repeated
  clipping/jump bugs support a geometry/lifecycle contract, not another renderer.
- The compiler thread records real bounded equation/code/graph capabilities and
  typed gaps. This review did not execute a comprehensive motif inventory and
  does not assert the absence of every uninspected mechanism.
- Visual acceptance and browser checks establish usability/implementation
  evidence, not independent learner transfer or retention.

## Important development gaps

1. **Transferable reading behavior.** Stable identities, local granularity,
   selected-state visibility and exact return must travel with authored material.
   Test branching/nonterminal structure and two simultaneous instances before
   claiming broadly reusable behavior.
2. **Bounded source-only authoring.** Demonstrate a new supported passage without
   editing reader CSS, selectors, motion code or compiler implementation. Permit
   honest new semantic authority when required; count it separately. Unsupported
   work should return a useful typed gap. One shared presentation repair should
   reach all opted-in callers while pinned editions retain explicit rebuild rules.
3. **Text/representation coordination.** Test long text with a short graph, long
   code with short prose, and nested detail. Keep the reading record available;
   preserve distinct renderer and domain semantics.
4. **Relational coverage.** Expand by consequential moves: use an earlier result,
   compare held-fixed assumptions, expose a validity condition, distinguish
   equivalence/implication/approximation/information loss, and switch perspective
   while keeping referents. Existing infrastructure is a starting point, not
   evidence that each learner interaction is solved.
5. **Pedagogical evidence.** Use a small, voluntary formative reading task with
   an unfamiliar reader, or a delayed personal return: can they locate the joint,
   explain its warrant and use the relation on a nearby case? Compare with the
   same strong static explanation. Do not infer a learning effect from liking
   motion or completing a control task; no telemetry/recruitment authorised here.

## Rework control and stopping rules

Keep semantic IDs, checked relations, assumptions, provenance and plain reading
durable. Keep geometry, emphasis, display defaults and motion choices replaceable.
Do not introduce a universal move schema or renderer from this review. Promote
shared APIs only after two meaningfully different callers expose the boundary.

Each experiment names its question, representative source, acceptance evidence,
rollback unit and stopping point. Completion yields a reusable capability, a
precise unsupported boundary, or a rejected design worth recording. It need not
yield another finished chapter. Separate personal study from the product queue;
capture interesting friction without converting every encounter into development.
