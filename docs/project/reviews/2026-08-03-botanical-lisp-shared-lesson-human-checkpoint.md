## Decisions for human review

1. **Botanical language:** Does the enclosure/branch/root/leaf/bud/fruit
   treatment make lexical binding and preserved occurrence identity easier to
   understand than native code alone?
2. **Choreography:** Are binding, reconstruction, evaluation gathering, and
   result settlement calm and distinct enough, with useful pauses and exact
   rewind?
3. **Salience:** At every checkpoint, is it obvious what to inspect without the
   plant metaphor competing with the code?
4. **Lesson ergonomics:** Do graph and code stages feel like one reading system
   while retaining the right domain-specific differences?
5. **Responsive behavior:** Are the phone stage, controls, prose cadence, and
   semantic navigation acceptable?

The useful response is `approve`, `repair` with concrete notes, or `reject the
botanical treatment while retaining the semantic asset`. Approval would permit
a bounded third-caller pass with generated solve-x; it would not by itself
promote a general botanical motif.

## API and promotion boundary

The executable classification lives in
`src/tutorial/kp-lesson-seam-ledger.ts`:

- shared mechanics are `shared-internal`;
- `KpTutorialLessonShell.svelte` is a
  `replaceable-first-party-host`;
- economics presentation is `domain-internal`;
- botanical presentation is `experimental-domain`.

No public tutorial SDK, shared scene graph, generic programming renderer,
botanical motif family, SvelteKit migration, Public Web work, generated solve-x
migration, or wider catalogue/lesson rollout is included in this checkpoint.

- Shared lesson extraction can be reviewed independently from botanical paint;
  economics remains the visual, URL, responsive, and performance baseline.
- The matrix-to-linear-map frontier remains tabled and the stable animation
  promotion ledger is unchanged.
