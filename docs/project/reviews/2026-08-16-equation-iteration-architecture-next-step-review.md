# Equation Iteration Architecture Next-Step Review

Date: 2026-08-16
Status: approved for execution across the current or successor Theseus run

## Question

How should KP order asset refinement, cross-operation motif pressure,
extensibility architecture, test-discipline reform, low-ROI test retirement,
equation migration, and governed LLM generation so that each tranche improves
iteration speed instead of adding another framework or central switch?

## Evidence

- The latest log-product promotion amended 54 files because semantic
  correction, multi-factor extension, routing, generated inventories,
  catalogue count ratchets, broad verification, and visual tuning occurred in
  one pass.
- The repository contains 1,394 test files, approximately 214,000 lines of
  test TypeScript, and 211 package scripts beginning with `test`, `check`,
  `verify`, or `visual`.
- Twelve catalogue tests repeat current totals such as 45, 62, or 89, while
  215 test files inspect implementation source directly.
- Asset loading, capability selection, surface selection, inventory
  classification, and some semantic visitors still rely on manually edited
  lists, prefixes, or closed functions. These are easy for a human or LLM to
  update incompletely.
- The accepted visual-testing policy separates durable truth, exemplar
  discovery, human selection, second-caller pressure, and promotion, but
  verification routing models risk without an explicit
  discovery/contract/promotion/release mode.
- The log-product semantic family, canonical compiler, native endpoints,
  shared clock, lazy pack, and catalogue host are strong enough to serve as the
  pressure path. Its revised presentation remains at a human checkpoint.

## Governing Extensibility Law

KP should be **open at declaration time and closed at execution time**.

- A new asset, family, operation, presentation recipe, or surface capability
  is added by contributing a typed immutable descriptor to the appropriate
  pack or build-time registry.
- Core compilers and hosts consume protocols and registries; they do not gain a
  new handwritten branch for every caller.
- Build generation may produce exhaustive closed dispatch with literal import
  paths so bundlers can tree-shake and split chunks. Generated switches are an
  implementation artifact, not the authoring API.
- Registries are explicitly composed and injected. Avoid side-effect imports,
  mutable global registration, stringly service locators, or one universal
  plugin registry.
- Unknown operations or missing capabilities fail with typed diagnostics. They
  never enter a generic visual fallback.

The desired shape is:

```text
open typed declarations
-> validation and build-time composition
-> generated exhaustive dispatch
-> small immutable runtime registries
-> closed deterministic execution
```

This reconciles extension without core edits, compile-time exhaustiveness,
tree-shaking, and LLM discoverability.

## Recommended Order

### 1. Complete the visible proof

Run planned slice `s25b` on the binary log-product exemplar only. Hold
semantic truth, endpoints, clock, catalogue, host, and accessibility fixed.
Change the local presentation policy, run focused preservation checks, capture
one deterministic review sheet, and stop for human approval.

This supplies the actual visual target and measures whether presentation is as
replaceable as intended.

### 2. Make iteration mode explicit

Extend verification selection from risk alone to a typed mode:

```text
discovery -> semantic preservation + sampler smoke + one exemplar capture
contract  -> typed laws + deterministic runtime + focused integration
promotion -> second caller + generated conformance + browser and bundle gates
release   -> full repository and supported-platform closure
```

Record time to reviewable capture, authored and generated files touched, test
files touched, and whether a new clock, renderer, adapter, registry, or dispatch
branch appeared. Known presentation-policy edits must not select an unrelated
visual exemplar or the complete repository gate.

### 3. Establish typed extension protocols and build-time registries

Define a small set of distinct registries rather than one universal registry:

1. **Family manifest:** asset IDs, literal lazy-pack path, declared
   capabilities, selected surface kind, and disposition.
2. **Semantic operation registry:** operation kind to validated compiler or
   typed unsupported result.
3. **Presentation recipe registry:** semantic capabilities and roles to a
   candidate or approved recipe; no asset IDs, geometry, or renderer nodes.
4. **Renderer/surface capability registry:** declared capability to a lazy
   adapter factory.

Registries should be immutable values composed per pack or application
boundary. Core visitors operate through protocols or data-owned child
enumeration rather than operation-name switches. Exhaustive switches that the
bundler needs are generated from manifests with literal imports.

Migrate only the log family first. Delete its parallel prefix tests,
hand-maintained membership, and manual capability branches in the same
rollback unit. Prove that adding another log-family caller changes semantic
data and its descriptor, not core dispatcher functions.

### 4. Generate projections and conformance from the declarations

Use the family and capability descriptors to generate:

- lazy-loader dispatch;
- catalogue membership and metadata;
- surface-capability selection;
- equation inventory and disposition projections;
- generic conformance cases; and
- the LLM-visible operation/capability catalogue used later.

Keep these generated outputs separate from runtime authority. The source
descriptor is the extension point; generated closed code is the auditable and
tree-shakable executable boundary.

### 5. Replace the highest-churn tests with stronger owners

Retire tests in bounded clusters as their replacement seams land:

1. **Catalogue totals:** replace repeated 45/62/89-style assertions with exact
   set equality between descriptors, generated manifests, loadable assets, and
   projected rows. Keep one generated aggregate summary.
2. **Capability import text:** replace regexes over source strings with
   descriptor validation, generated import-graph closure, and production
   bundle attribution.
3. **Closed-dispatch enumeration:** generate conformance over every registry
   entry; do not add a test and core switch edit for each caller.
4. **Renderer source shape:** replace source-byte, vocabulary, function-count,
   and exact dependency-list ratchets when a public API, import boundary,
   nominal type, bundle measure, or runtime property tests the real promise.

Delete superseded tests when the stronger owner lands. Do not keep both as
reassurance. These tranches should be net-negative in duplicate assertions and
preferably test files.

### 6. Promote the homomorphic-decomposition crossover

After binary approval and the thinner extension path, pressure the existing
three-factor product for cardinality and log quotient for structural
difference. A shared candidate may name semantic presentation phases such as
source-application release, continuant redistribution, target-application
reception, and target-relation resolution. Timing, geometry, easing, and paint
remain presentation/renderer policy.

Promote only if product and quotient register against one recipe capability
without a new clock, renderer, identity law, core switch branch, or
caller-authored geometry. Remove the superseded production wrapper-splitting
path and its uniquely owned tests after approval.

### 7. Migrate equation families with adjacent switch and test retirement

Resume migration wave A, then B, then C through the declarative entrance:

- Wave A: operation-plan families and approved motifs.
- Wave B: structurally demanding native-math families such as fractions and
  radicals, retaining distinct presentation recipes.
- Wave C: generated bespoke, diagnostic, static-only, unsupported, and retired
  rows.

For each family, add semantic bindings and declared capabilities, generate its
projections, prove focused conformance, then delete the bypass, manual routing
branch, compatibility owner, repeated caller tests, and obsolete scripts beside
its final caller. Migration is incomplete while the old production path or its
duplicate test authority remains.

### 8. Consolidate test discipline around invariant ownership

After migration has removed most parallel paths, consolidate shared laws into
parameterized harnesses for correspondence, provenance, endpoint ownership,
seek/rewind/interruption, reduced motion, registry closure, manifest closure,
and bundle capabilities. Each invariant gets one declared owner and the
cheapest reliable test layer.

Do not reorganize all test directories for neatness. Track test duration,
flake rate, and meaningful historical failures before further deletion.

### 9. Connect governed LLM generation

Only after equation authority is singular should the model-facing draft path
enumerate available operations, semantic roles, IDs, traits, and capabilities
from the same typed declarations.

Models author mathematical states, correspondence intent, teaching intent, and
bindings. KP selects recipes and owns timing, paths, geometry, renderers,
clocks, and fallbacks. Unsupported combinations return typed repair gaps.
Measure a valid draft on first attempt or after one typed repair, not merely
JSON-schema validity.

The removal of manual switches materially improves model accuracy: there is
one discoverable contribution protocol, and a generated conformance check
proves that every declaration reached every required projection.

### 10. Pressure the upper boundary across domains

Use one approved graph and one approved code animation to confirm that asset
identity, capability declaration, lazy loading, host lifecycle, shared clock,
review capture, semantic addresses, and verification modes cross domains while
equation compilers and recipes do not.

This is the decoupling proof. Do not route graphs, code, Scheme recursion, or
3D through the equation semantic-motion compiler.

### 11. Run release closure and compare iteration economics

Run broad type, architecture, browser, accessibility, bundle, deterministic,
and performance gates after migration and LLM entry stabilize. Compare the
measured inner loop with the log-product baseline.

## Success Measures

- A visual alternative changes one to three authored source files, no generated
  inventories, and reaches reviewable capture in roughly 5-15 minutes.
- A same-family asset contributes semantic data and a descriptor without
  manual loader, capability, inventory, count, or core-dispatch edits.
- Runtime dispatch remains exhaustive and tree-shakable because it is generated
  from validated declarations.
- A migration family deletes its bypass, handwritten switch cases, and
  redundant tests in the same unit.
- No current moving equation bypasses the canonical compiler entrance.
- High-value semantic failures remain localized while release certification is
  no longer an inner-loop default.
- Governed LLM generation selects valid operations and roles on the first
  attempt or after one typed repair, with no generic fallback.
- Graph and code callers reuse upper-level contracts without importing
  equation-specific semantic or presentation machinery.

## Recommendation

Keep `s25b` as the immediate next action. If its checkpoint passes, insert one
bounded iteration-path compression tranche before migration wave A:

```text
verification modes
-> typed extension protocols and log-family descriptors
-> generated dispatch and projections
-> retirement of the first high-churn test clusters
```

Then promote homomorphic decomposition through quotient pressure and resume
the exhaustive equation waves through the compressed front door.

Do not start with a global mutable registry, universal plugin system, test
purge, directory move, or cross-domain compiler. Deep architecture is justified
now where it eliminates an observed core edit, duplicated authority, or
verification tax.
